The pure arithmetic reserves one maximum-sized record for each outstanding ACK and stop, the seal, and, while open, the close. Registration and already written permit/evidence count towards the supplied event and byte totals. Schema initialization checks the contract against the same constants used by the arithmetic. SQL CHECK constraints reject incompatible values. Contract reads are bounded to two rows. Migration is transactional and does not scan, reinterpret, or change historical events.

This is not a live capacity migration or durable reservation. Existing v2 registry and v6 legacy validation still enforce 130 events, 16,384 bytes per record and 262,144 bytes per history. The arithmetic is not wired to admission: it assumes a future authenticated caller establishes truthful counts in an owned transaction and persistently reserves them. Public permit, ACK, stop and seal remain disabled; inert records remain unauthenticated and launch_unknown. Supporting 386 preseal/387 total actual events requires a reviewed versioned history format, bounded replay/read budgets, schema compatibility, authenticated receipt sizes and same-transaction durable reservation. This contract alone provides no assurance of those properties.

The run-wide cancellation proof has a 4 MiB byte budget, less than the prospective 6,340,608-byte single-stream maximum even before other records and accounting overhead. The prospective maximum therefore does not imply cancellation completion; over-budget cases must remain held. This change does not increase that gate. No claim is made about SQL page I/O or CPU for legacy v6 migration scans.
