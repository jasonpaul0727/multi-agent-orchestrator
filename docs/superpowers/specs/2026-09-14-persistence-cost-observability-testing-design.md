# Multi-Agent Orchestrator：持久化、成本统计、可观测性与测试设计

日期：2026-09-14

状态：方案方向已获用户确认，等待用户审阅书面规格

## 1. 目标

本规格补齐 V1 的持久化、成本统计、可观测性和测试边界，并为已经确认的任务生命周期、模型路由、权限安全与审批规格提供稳定的存储和恢复接口。

V1 的核心目标是：

- 以事件存储作为 Run、DAG、节点、attempt、安全授权和外部副作用的唯一事实来源；
- 在本地 CLI 和 MCP Server 并发运行时保持可重放、可恢复和可审计；
- 将模型 Token、工具费用、预算预留和结果不明的费用统一纳入账本；
- 让一次任务能够从用户请求追踪到模型、工具、审批、产物和最终交付；
- 让状态机、预算、策略、审批、崩溃恢复和安全边界可以通过自动化测试验收。

## 2. 范围与非目标

本规格包含：

- 本地 SQLite 事件存储、快照、幂等和版本校验；
- Run、图、节点、attempt、路由、安全和审批事件的逻辑数据模型；
- Artifact Store 的引用、哈希、生命周期和访问边界；
- Token、价格、费用、预算预留、结算和结果不明的账本语义；
- 结构化日志、追踪、指标、审计投影和去敏规则；
- 重启恢复、事件重放、故障隔离和一致性检查；
- 单元、属性、集成、崩溃矩阵、安全和端到端验收测试。

本规格不包含：

- 远程多租户服务、云端事件总线或在线控制台；
- 具体 CLI/MCP 命令格式和 UI；
- 特定 SQLite ORM、迁移框架或 OpenTelemetry SDK；
- 厂商价格的静态默认值；
- 删除安全审计事件或绕过控制平面的清理机制。

V1 可以在未来增加 PostgreSQL、对象存储或远程观测后端，但不能改变事件、预算、审计和恢复语义。

## 3. 已确认的总体决策

### 3.1 本地优先

V1 使用一个受 Orchestrator 控制的 SQLite 数据库文件作为默认事件存储。数据库放在控制目录，不放在普通 Agent 工作区内，也不允许 Worker 直接打开。

SQLite 采用 WAL 模式，允许并发读并把写入收敛到 SQLite 事务。写事务使用明确的超时、版本校验和重试上限；无法获得一致写入时，控制层阻塞新授权和副作用，而不是放宽校验。

### 3.2 接口与后端分离

编排核心只依赖以下逻辑接口：

- EventStore：追加事件、读取流、按版本 CAS、重放和校验；
- SnapshotStore：保存和读取已验证的聚合快照；
- BudgetLedger：预留、结算、释放和查询额度；
- ArtifactStore：写入、读取、引用计数和验证产物；
- ObservationSink：接收结构化日志、追踪和指标；
- ProjectionReader：查询由事件重建的只读视图。

SQLite 是这些接口的 V1 实现。未来后端必须通过同一接口满足事件不可变、幂等、版本 CAS、审计追加和失败关闭要求。

### 3.3 事件优先

有效状态变化必须先追加事件，再更新投影或唤醒调度器。投影、缓存和快照损坏时，可以从事件流重建；事件追加失败时，不得签发新 Grant、创建新 attempt 或执行新的外部副作用。

## 4. 总体架构与数据流

数据流为：

CLI/MCP Server -> Orchestration Core -> Control Plane -> EventStore/BudgetLedger/ArtifactStore -> Model Gateway/Tool Gateway

模型和 Worker 只能经 Gateway 提交请求。Gateway 和控制层负责把动作、路由、预算、权限、审批和结果写入事件存储；Worker 不能直接修改数据库、快照、预算账本或审计投影。

控制层的主要组件为：

- Event Store：保存不可变事件流，维护 Run、节点、attempt、策略和安全事件的顺序；
- Snapshot Manager：在重放成本达到阈值时生成可验证快照，不替代事件；
- Budget Ledger：管理 Token、金额、并发、Agent 数量和调用深度的预留与释放；
- Cost Calculator：使用冻结的价格和估算器版本计算最坏成本与实际成本；
- Artifact Store：以哈希保存模型结果、工具输出、检查点和交付物；
- Observation Pipeline：从事件和运行时 span 生成日志、指标、追踪和只读查询；
- Recovery Manager：重启时验证事件链、恢复快照、重建投影并重新调度可安全恢复的节点。

## 5. 事件存储

### 5.1 事件字段

每个事件至少包含：

- event_id：全局唯一事件 ID；
- stream_type、stream_id、stream_version：事件流和流内单调版本；
- event_type、schema_version：事件类型和载荷版本；
- occurred_at、event_time：写入时间和用于重放的事件时间；
- run_id、node_id、attempt_id、agent_id：适用时的任务关联；
- graph_version、fencing_generation：图版本和执行栅栏；
- causation_id、correlation_id、actor_type、actor_id：因果链和主体；
- payload_json、payload_hash、redaction_version：规范化载荷、摘要和去敏版本；
- idempotency_key：外部回执、重复投递和恢复操作的幂等键。

事件载荷使用稳定的 JSON 编码和明确的 schema 版本。秘密值、原始凭据、未去敏的敏感请求正文和受保护路径内容不得写入事件。

### 5.2 追加与一致性

append(stream_id, expected_version, events, idempotency_key) 必须在单个 SQLite 事务中完成：

1. 检查调用方拥有有效的控制层身份；
2. 检查 expected_version 与当前流版本一致；
3. 检查事件序号、事件类型、载荷 schema 和幂等键；
4. 追加全部事件；
5. 更新聚合版本并提交事务；
6. 提交成功后才通知投影和调度器。

版本不一致返回 stale，调用方必须读取新事件并创建新的命令或 RoutingRequest；不得原地覆盖旧决定。相同幂等键重复提交时返回第一次提交结果，不产生重复事件。不同载荷复用同一幂等键必须失败。

数据库至少保证以下唯一性：

- event_id 全局唯一；
- (stream_type, stream_id, stream_version) 唯一；
- (stream_id, idempotency_key) 唯一；
- 安全事件和外部副作用事件使用独立的不可变流序号。

### 5.3 逻辑事件流

V1 至少包含以下逻辑流：

- run：Run 创建、阶段转换、暂停、恢复、取消、终态和交付；
- graph：图版本、节点、依赖、扩展、细化和合并；
- node：节点状态、契约、验证、失败、重试和阻塞；
- attempt：租约、路由、模型/工具调用、检查点和结果；
- security：策略、Grant、审批、隔离、撤销和安全事件；
- budget：额度信封、预留、释放、结算、调整和冻结；
- health：provider/model 健康聚合和探测租约；
- audit：去敏审计和外部副作用证据。

安全规格中的 EffectIntentRecorded 必须在外部副作用发送前落入可提交的事件事务。ApprovalGrant 的消费、预算预留和 EffectIntent 的写入必须由 Gateway 通过可验证的原子流程完成。

### 5.4 快照与恢复

快照包含：

- 聚合类型、聚合 ID、截至事件版本；
- 完整状态摘要和规范化哈希；
- 创建时的 schema、配置、策略和注册表版本；
- 快照创建事件 ID 和校验信息。

快照只用于减少重放事件数。恢复时必须先验证快照，再从下一事件版本开始重放；哈希、版本或 schema 不匹配时丢弃快照并从事件流重建。事件链损坏或审计流不可验证时，系统进入安全规格规定的 Fatal 或 Quarantined 状态。

### 5.5 保留与清理

V1 不自动删除事件和安全审计流。快照可以替代计算但不能替代或覆盖历史事件。Artifact Store 的清理只能删除已终态 Run 中没有有效引用、没有未决副作用、没有恢复责任的临时产物，并必须先记录清理意图和结果。安全审计的长期删除策略不在 V1 范围内。

## 6. Artifact Store

产物按 sha256 加摘要值内容寻址，元数据至少包含：

- 产物类型、大小、媒体类型和创建时间；
- 来源 Run、节点、attempt、工具或模型；
- 内容摘要、schema 版本和去敏状态；
- 允许读取的下游节点和权限档位；
- 生命周期状态、引用关系和清理条件。

写入采用临时对象、哈希验证、原子提交三步流程。Worker 只能通过 Gateway 写入私有暂存或提交候选产物，不能直接写入最终 Artifact Store。read-only attempt 的临时目录不自动成为下游可见产物，必须经控制层接收并记录引用。

产物内容与事件载荷分离保存。事件中只保存引用、摘要和访问边界，避免大型模型输出、二进制文件和工作区内容膨胀事件流。

## 7. 预算与成本账本

### 7.1 统一计量

预算和费用使用整数最小货币单位，必须记录币种。Token 使用量至少区分：

- 输入 Token；
- 输出 Token；
- reasoning Token（供应商提供时）；
- cached input Token（供应商提供时）；
- 工具或供应商附加费用；
- 本地零成本调用的 Token 消耗。

模型价格、汇率、Tokenizer/估算器和附加费必须以版本化快照写入 RoutingRequest 与 CostEstimate。缺少或过期价格时，付费模型不能通过自动路由。

### 7.2 费用状态

每次模型或工具调用通过以下账本事件管理费用：

1. CostEstimateCreated：按最坏输入、输出、重试和附加费用估算上界；
2. BudgetReserved：在调度接受事务中预留 Token、金额、并发和相关配额；
3. UsageObserved：记录供应商回执或本地计数；
4. CostCommitted：按冻结价格结算实际成本；
5. BudgetReleased：释放未使用的预留；
6. CostAdjusted：仅用于供应商补账或核对，必须引用原始记录和原因。

一次调用的预算预留、RoutingDecision 接受、并发额度和 attempt 租约必须原子提交。调用完成后，结算和释放也必须以幂等键提交，重复回执不能重复扣费。

### 7.3 结果不明和崩溃

如果模型、工具或外部副作用的结果不明，系统保留最坏成本预留，并把费用标记为 unknown。未经核对，不能释放预留、自动重发或把 Run 标记为成本结算完成。

模型调用结果可查询时，通过供应商 request ID 或 Gateway 幂等键核对；不可查询时进入人工处置或生命周期规格规定的 AwaitingReconciliation。核对结果必须追加新的事件，不得改写原始费用记录。

### 7.4 预算查询

账本对每个 Run、节点、attempt 和角色提供：

- 上限、已预留、已使用、已释放和剩余额度；
- Token 与金额的分别统计；
- 结果不明额度；
- 预留版本和最近一次变更事件；
- 被预算阻塞的节点及其可恢复条件。

预算只会收紧或消耗，不会通过模型输出、项目配置或子 Agent 自动扩大。用户授权的新预算必须通过安全规格规定的 RunAuthorization 事件，并受系统和调用方硬信封限制。

## 8. 可观测性

### 8.1 结构化日志

运行时日志使用结构化字段，不把日志当作状态事实。每条日志尽量包含：

- 时间、级别、组件和版本；
- run_id、node_id、attempt_id、agent_id；
- provider、model、role、preset、task_class；
- correlation、causation、fencing generation 和事件版本；
- latency、重试层级、Token、费用、阻塞原因或安全决策；
- 去敏后的错误类型和外部 request ID。

日志写入前执行秘密指纹、已知密钥和受保护路径的脱敏。原始 Prompt、凭据、完整网页响应、命令环境和未授权工作区内容不能进入普通日志。

### 8.2 追踪

每个 Run 产生根 trace；Planning、Routing、Dispatch、Model Gateway、Tool Gateway、Approval、Artifact、Verification 和 Final Review 建立子 span。span 只保存低敏元数据和事件引用，完整结果放在受权限控制的 Artifact Store。

V1 采用内部稳定的 trace/span 字段和 ObservationSink 接口。是否接入 OpenTelemetry SDK 属于实现选择，不能改变事件 ID、因果链和去敏约束。

### 8.3 指标

至少提供以下只读指标：

- Run、节点和 attempt 的数量及各状态持续时间；
- 规划、路由、模型调用、工具调用、验证和交付延迟；
- 各 provider/model/role/preset 的调用次数、失败率、重试率和升级率；
- 输入、输出、reasoning、cached Token 和实际费用；
- 预算预留、释放、阻塞和结果不明额度；
- 安全拒绝、审批等待、审批耗时、隔离失败和审计写入失败；
- Artifact 写入、读取、哈希校验失败和清理数量；
- SQLite 写入等待、CAS 失败、重放耗时和恢复结果。

指标由事件或运行时记录派生。派生指标错误不能改变任务状态；指标写入失败时，控制面仍须优先保证事件、授权和副作用安全。

### 8.4 只读解释

系统提供两类查询：

- 精确查询：按事件、Run、节点、attempt 或 RoutingDecision ID 重放历史事实；
- 汇总查询：从投影读取状态、预算、费用、路由解释、审批和审计摘要。

投影落后时返回其事件版本和滞后状态，不能把旧投影误报为实时状态。需要实时判断的调度、授权和预算检查必须直接读取控制层的当前版本。

## 9. 启动、恢复与故障处置

控制平面启动时依次执行：

1. 检查 SQLite schema 和迁移版本；
2. 验证事件流序号、哈希和不可变约束；
3. 读取并验证最新快照；
4. 重放快照后的事件；
5. 重建只读投影和预算账本；
6. 标记租约过期、未完成的 attempt 和结果不明的外部效果；
7. 按任务生命周期和安全规格重新计算可恢复节点；
8. 只有事件、预算、安全和审计不变量全部通过，才恢复新调度。

恢复必须保留已接受的节点结果、产物、Token、费用和验证证据。租约失效、审计不可写、事件链损坏、预算账本不一致或隔离能力不可验证时，系统停止新授权和副作用，并按既定规格进入 Blocked、Fatal 或 Quarantined。

SQLite 事务提交成功但进程在通知投影前崩溃时，重启后的投影重建负责补发行为。通知成功但调度器崩溃时，幂等键和事件版本负责避免重复 attempt 或重复扣费。

## 10. 测试策略

### 10.1 单元与属性测试

覆盖：

- 事件 schema、规范化、哈希、版本和幂等键；
- 状态机、DAG 追加、fencing 和检查点；
- 预算预留、结算、释放、结果不明和整数金额计算；
- 价格快照、Token 估算器和模型路由解释；
- 投影从事件流重建的一致性；
- 规则“拒绝优先”、授权信封和审计去敏。

属性测试验证：事件只追加、版本不会倒退、同一幂等操作最多产生一次事实、账本不会凭空增加额度、任何投影均可由事件重建。

### 10.2 SQLite 集成测试

覆盖：

- WAL 并发读、写事务和 busy timeout；
- 两个调度器竞争同一预算、租约、ApprovalGrant 或 event version；
- CAS 成功、失败和重试；
- 提交后通知前崩溃、恢复后投影补建；
- 快照创建、损坏、回退和重放；
- schema 迁移、旧事件版本兼容和失败回滚。

### 10.3 安全与权限契约测试

复用权限安全规格的验收项，并确认其证据落入本规格的事件与观察接口：

- 工作区、符号链接、junction、reparse point、硬链接和 Git 控制目录逃逸；
- Worker 无原始网络、密钥、数据库和控制面直连；
- Grant 参数变化、撤销、过期、generation 变化和并发消费；
- EffectIntent 写入顺序、结果不明、核对和禁止自动重发；
- 审计不可写、事件链损坏和秘密脱敏失败时的失败关闭。

### 10.4 崩溃矩阵

至少覆盖以下边界：

- 事件追加前；
- 事件追加后、投影通知前；
- 预算预留后、模型调用前；
- EffectIntent 后、外部发送前；
- 外部发送后、回执前；
- 回执后、结算提交前；
- ApprovalGrant 消费前后；
- 取消、暂停、租约过期和重复投递。

每个场景都要验证：是否重复副作用、是否重复扣费、是否错误释放预算、是否丢失证据、是否能回到合法生命周期状态。

### 10.5 端到端验收

至少执行以下端到端路径：

1. 本地 CLI 创建 Run，规划 DAG，路由模型，执行工具，产生产物并完成 Final Review；
2. MCP Server 与 CLI 同时读取状态，但只有合法控制层事务可以发出租约和工具动作；
3. economic、balanced、quality 和 custom 预设使用同一账本和安全约束；
4. 低成本子任务使用兼容模型，复杂或高风险节点触发高能力模型和独立 Reviewer；
5. 中途崩溃重启后，事件、预算、产物、审计和结果不丢失且不重复执行；
6. 审批、撤销、隔离不可用、模型不可用和结果不明路径均按照规格停止或等待。

## 11. 完成条件

本模块完成时必须满足：

1. 所有有效状态变化都能从不可变事件流重建；
2. SQLite 并发、CAS、幂等和崩溃恢复不会产生重复 attempt、重复扣费或未授权副作用；
3. 预算、Token、费用和结果不明额度可按 Run、节点、attempt、角色和模型解释；
4. 日志、追踪、指标和审计可关联到同一条因果链，并且不泄漏秘密；
5. 快照、投影和缓存损坏时可以回到事件流恢复；
6. 生命周期、路由、权限安全与审批规格的跨模块契约测试全部通过；
7. 测试覆盖配置、隔离、网络、密钥、审批、恢复、并发和副作用崩溃矩阵。
