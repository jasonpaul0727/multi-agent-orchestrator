# P5 Trusted Candidate Publication

**Date:** 2026-10-11 (America/Los_Angeles)
**Status:** Design draft, self-reviewed; independent architectural review pending. No implementation or implementation plan is authorized by this document alone.
**Source BASE:** `1cbf99c89cb54cfeb6b5bbdcb697a1bf25d94c48`
**Delivery boundary:** A trusted host publication prerequisite. Production Worker execution remains blocked-only.

## Intent and authority

The human explicitly requested finishing each task, self-planning/reviewing the next task and proceeding when sound, using subagents and pushing completed reviewed stages. This authorizes design preparation; it is not a fabricated human approval of a written spec that did not yet exist. Independent design review, a separately reviewed implementation plan, source acceptance and independent source review remain subsequent gates. This document neither runs them nor claims their outcomes.

The pure `decode_worker_output` now supplies bounded bytes and child-proposed references. This design adds the narrow host boundary needed to retain those bytes and publish one coherent candidate set under current Attempt authority. A well-formed frame, a matching digest, a publication receipt and a verifier proposal are four different things; none is an Attempt success decision.

Threats are untrusted Worker data, concurrent host operations and process/database/filesystem failures. The host control plane, its private store and UTC clock remain trusted under the existing Linux/systemd assumptions. This is not protection against a hostile same-UID host, arbitrary Python code executing inside the host, or memory/swap/core-dump disclosure.

## Existing interfaces and the constraint they impose

At BASE:

- `runtime/worker_output.py` validates exact bounded bytes, full context, canonical Base64, unique digest sets, actual sizes and hashes. Its frozen return objects grant no origin or authority; callers can construct objects unsafely.
- `WorkerInputService.prepare_worker_task` reconstructs an input-bound task from durable role/context and caller re-supplied exact text. There are no input artifacts or Tool capabilities in this narrow profile; the decoded content cap is 16,384 bytes.
- `Scheduler.resolve_verification_binding` reconstructs the full original admission context. `resolve_active_attempt` checks accepted route, active lease, cancellation, Agent and reserved budget. Both nest within `SQLiteEventStore.append_checked`.
- `ArtifactStore.publish_bytes` creates one random publication identity, stages bytes, acquires a digest filesystem lock followed by the process-wide `_PUBLICATION_LOCK`, writes SQLite intent, installs an immutable object and appends one `ArtifactPublished` event. It cannot atomically publish an entire set or receive a stable publication identity today.
- `admit_candidate_artifacts` and `IsolatedVerifierProcess.verify` currently check per-reference publication provenance, not a durable whole-set identity. `ArtifactStore.read_bytes` requires a trusted digest-bound grant and matching publication scope. An intent or bare blob is insufficient for a read.
- `finish_verified_attempt` owns successful lifecycle, usage and resource release. Publication must not call it or produce its evidence.

There is also an indirect existing lock inversion: `resolve_active_attempt` calls `RunRecoveryCoordinator.recover` while holding SQLite; recovery calls `pending_publications_for_run`, which acquires digest locks. Startup and other Scheduler recovery paths also invoke recovery under SQLite. Avoiding only a direct `publish_bytes` call in a Scheduler callback does not solve the problem. The limited recovery separation below is a prerequisite to this design, not an optional optimization.

## Alternatives and choice

| Alternative | Assessment |
| --- | --- |
| Call existing `publish_bytes` repeatedly with active checks before/after | Reject. A crash or cancellation can leave an arbitrary subset with published metadata and reading eligibility. Retrying creates new publication IDs. A post-check cannot undo filesystem effects or already visible authority. |
| Hold Scheduler SQLite across existing publication; or guard each publication separately | Reject. The first reverses existing lock order and keeps filesystem operations inside SQLite. Per-artifact guards still admit subsets and different authority instants. Acquiring all digest locks first would also require restructuring the existing process mutex and still keeps filesystem work under the final lock if used naively. |
| Publish provisional `ArtifactPublished` records and teach every reader to hide them until a marker | Viable but larger. A missed grant/metadata/inventory consumer would expose a partial publication, and existing provenance matching is not a visibility barrier. |
| Durable set preparation, retained blob installation, then atomic metadata plus set commit | **Selected.** Reuses the existing append-only SQLite store, per-digest installation machinery and intent inventory. New bytes have no new readable publication until a single final transaction publishes every member. A small exact-set gate prevents later subset/mixed-set admission. |

The selection requires new internal ArtifactStore staging/finalization operations. These are proposed interfaces, not APIs that already exist. Calling private `_record_metadata` from a new service without its specified invariants is not an implementation of this design.

## Public host boundary

Propose a ready-gated `ControlPlaneApplication.publish_worker_candidate(*, run_id, node_id, attempt_id, fencing_generation, task_text, payload)` backed by a private `CandidatePublicationService`. `payload` is exact nonempty `bytes`, maximum 1,048,576 bytes; identity fields use the exact existing AttemptContext identifier/generation rules. No model instances, paths, directories, store handles, decoded return objects, grant bodies, caller timestamps, role, classification, source, metadata overrides, usage or no-effect claims are public request fields.

The host caller may supply identity, raw frame and exact task text for re-supply. Text is checked against the original input manifest commitment using durable role, as in WorkerInputService, and is never persisted or logged. This is an explicitly trusted host API; possession of matching fields does not authenticate a child process. Future transport must establish the producing process and confirmed termination before invoking it. This slice does not connect that transport or claim process attestation.

The service receives the exact same `SQLiteEventStore`, Scheduler and ArtifactStore objects from trusted composition. Separate databases, append-only fake adapters, an unavailable store, or transaction re-entry without the required recovery inventory fail closed. Clock injection is composition/test-only and must return aware UTC; request callers cannot backdate a decision.

Only `candidate` is publishable. A valid `blocked` or `failed` frame returns `candidate_publication_invalid` without writing a candidate event. Its failure text/code is never turned into publication authority.

The service constructs a fresh task from durable authority and explicit text, invokes the pure decoder, then validates the result at the publication trust crossing. Rebuild expected schemas recursively; reject unknown surviving fields/extras, bool-as-int, field-overriding subclasses, invalid tuples, references or bytes. Require exact immutable bytes, unique complete digest mapping, SHA-256/actual size/aggregate caps and exact full context again. A frozen dataclass or Pydantic instance is not evidence. An injected or unsafely constructed decoder return must fail before preparation. Reject arbitrary metadata rather than trusting a type annotation or field-only copy that discards unknown data.

Use all original durable bindings: Run, Node, Attempt, generation, Agent, current graph version, original input manifest, frozen EffectiveConfig/Registry/policy, routing decision and planning contract; accepted route/model/provider/reservation; active Agent/Attempt status; reserved budget; no cancelling/cancelled Run; exact accepted lease and fencing generation. Recheck the full planning contract/role and config relationships used by WorkerInputService, not only the hash echoed by the child. The current narrow profile requires the original `maestro.artifact-verification/v1` binding with exactly `("artifact-integrity",)` required checks and empty inputs/capabilities; it cannot retrofit a missing original admission.

## Fixed host metadata policy

Version 1 uses one host-owned policy `maestro.candidate-policy.v1`:

- Every proposed reference must specify `artifact_type="worker-candidate"` and `media_type="application/octet-stream"`. Other values reject. These literal labels describe unverified bytes; the publisher does not infer MIME types, execute bytes or claim semantics.
- The host recomputes digest and size. It supplies `schema_version=1`, `redaction_state="unknown"`, `readable_scope=(run_id,)`, `references=()`, and `lifecycle_state="temporary"`. No wildcard scope, child-controlled redaction assertion or verified/success lifecycle value is accepted.
- `source` contains the five existing exact provenance fields (generation encoded as its canonical positive decimal string), plus `publication_protocol="maestro.candidate-publication.v1"` and `candidate_set_id`. It does not fabricate a Tool or model-produced provenance claim.
- Full context and reservation/route bindings live in the set journal. An artifact's narrow existing source fields alone are insufficient to recover candidate authority.
- `created_at` is the host preparation time, frozen for retry; `publication_id` is deterministic as defined below. A later commit timestamp does not rewrite the prepared record.

This fixed policy avoids adding an extensible policy/plugin mechanism to the prerequisite. Later typed artifacts need a separately reviewed host policy. Different Runs may have identical immutable content; each gets distinct Run-scoped publication metadata. A grant for Run A must not acquire Run B's provenance or bytes merely because a pending B candidate shares the digest. Existing independently authorized A publications remain readable under their own existing grants; staging cannot revoke that authority and does not create B authority.

## Durable identity and event contract

Use a new `candidate_publications` stream per Run, with two permitted event types: `CandidatePublicationPrepared` and `CandidatePublicationCommitted`, schema `maestro.candidate-publication.v1`. This is an event contract addition, not a new SQLite table or migration. Reject unknown types/versions/fields and type substitutions during append and replay.

Canonical JSON everywhere in this protocol means sorted keys, compact separators, `ensure_ascii=False`, `allow_nan=False`, strict UTF-8. Sort member references by digest; reference order in a received WorkerResult is not set identity. Let `H(tag, value)` be `sha256:` plus lowercase SHA-256 of UTF-8 `tag`, a zero byte, then canonical JSON of `value`.

1. `request_id = H("maestro.candidate-request.v1", {run_id,node_id,attempt_id,fencing_generation})`. Exactly one proposed set may be prepared for an Attempt/generation. There is no user-selected idempotency key and no replacement/append API.
2. `result_id_hash = H("maestro.candidate-result-id.v1", result.result_id)`. Persist the hash, not the arbitrary child identifier string.
3. `set_id = H("maestro.candidate-set.v1", {request_id,context,result_id_hash,policy_id,output_byte_limit,members})`. `members` is the sorted full host-policy ArtifactRef list. Bytes are bound by their recomputed digests and sizes; duplicate digests are rejected before hashing. `output_byte_limit` is 16,384 for this profile.
4. Each member's `publication_id` is `candidate-v1:` plus the hexadecimal part of `H("maestro.candidate-member.v1", {set_id,digest})`. This namespace is reserved; the ordinary `publish_bytes` API must reject its use through future overrides and reject the candidate protocol/source keys. It currently generates its own random ID and has no publication-ID parameter.

The prepared payload has exactly `schema`, `request_id`, `set_id`, `context`, `result_id_hash`, `policy_id`, `output_byte_limit`, `reservation_id`, `accepted_route_id`, `accepted_at`, `lease_expires_at`, `prepared_at`, `authority_heads`, `members`, and `records`. `records` is the sorted complete `ArtifactRecord.to_event_payload()` list, one per member. All timestamps are aware UTC ISO strings normalized to six fractional digits and `+00:00`; other representations reject in this new protocol. All deterministic fields must be recomputed and compared. `prepared_hash = H("maestro.candidate-prepared.v1", prepared_payload)` is referenced by the commit.

The committed payload has exactly `schema`, `request_id`, `set_id`, `prepared_hash`, `authority_heads`, and `committed_at`. `committed_at` is the final authority-decision clock sample defined in phase D, not its earlier after-lock sample or the database commit/response time. The journal resolves its complete record through the unique preparation; it cannot choose a subset or new metadata. Idempotency keys are `candidate-prepare:<request hex>` and `candidate-commit:<request hex>`. Headers require exact Run/Node/Attempt/generation, `correlation_id=run_id`, and `causation_id=set_id`; stream ID must equal Run. Event-store integrity, consecutive stream versions and canonical hashes are necessary but do not replace protocol replay checks.

`authority_heads` is the sorted exact five-element array for streams `run/<run_id>`, `run_lifecycle/<run_id>`, `agent_registry/<run_id>`, `budget/<run_id>` and `scheduler/global`, sampled within the respective preparation/final transaction after authority validation. Each element has exactly `stream_type`, `stream_id`, positive integer `version`, `event_id` and `payload_hash` of that head. These streams all exist for an accepted Attempt. Replay validates every prefix through the referenced version and independently reconstructs lifecycle, Agent, reservation, route and graph state there. Referenced heads must exist and match exactly; commit heads cannot precede preparation heads. This is new persisted historical witness data: BASE exposes per-stream versions, not a cross-stream total-order API. Do not infer transaction order from event IDs or wall-clock `occurred_at`. Trusted host creation under one SQLite write lock establishes the coherent snapshot; hashes and replay detect inconsistent persisted references, not forgery by a hostile host rewriting its database.

The initial transaction also appends each corresponding existing `ArtifactPublicationIntent` with its complete frozen record under `artifact-intent:<publication_id>`. Existing artifact-stream event shape remains compatible. The final transaction appends matching `ArtifactPublished` events under `artifact-publication:<publication_id>`. New candidate artifact events use the same complete execution headers as their set events. Replay validates intent/publication payload and header equality against the set, including fields that the generic historical ArtifactRecord parser normalizes or permits absent.

Identical concurrent requests converge on one preparation and one commitment. Same Attempt with changed result ID, context, bytes, count or metadata conflicts, including after a crash; no second set is admitted. Reordered references/blobs or JSON whitespace produce the same identity after decoding. Duplicate/partial submissions reject or conflict; a request is always the entire set. Identical digests across different Attempts/Runs reuse bytes but retain separate preparation, publication and provenance identities. Same digest with inconsistent size is corruption, never a merge.

## Transaction and installation protocol

The complete operation has the following states:

`validated in memory -> prepared durably -> blobs retained -> committed durably`

Only the last state has new `ArtifactPublished` metadata and an eligible candidate set. A retained blob is not a durable successful output. No event transitions a Node or Attempt, invokes a verifier, settles usage or releases a slot.

### A. Read and validate

First read the exact request's durable journal state. A known committed request takes the historical comparison path below; it does not require a new active task. Otherwise, outside any SQLite write transaction, obtain the required recovery inventory described below and prepare/revalidate the bounded task/frame. An early active check saves wasted work, but is not the authorization point. No payload, text or decoded bytes enter the journal. New invalid/oversized/noncandidate requests fail with no candidate effects.

### B. Prepare the whole set

Enter a short outer `append_checked` transaction on the candidate Run stream. Validate the inventory version witness, complete existing candidate stream and conflicts/caps. Sample trusted time after obtaining SQLite; resolve the full current verification binding and all relationships above using database-only recovery. Reject a backward time relative to accepted/prepared times and require `accepted_at <= now < lease_expires_at`.

If no matching preparation exists, append the preparation and every member's intent in this same transaction. The store's metadata-only intent operation must use the identical event connection and no digest locks/filesystem work. Either all intents and the set preparation commit, or none do. There is no installed candidate byte before this transaction is known committed. If the commit outcome is unknown, re-read on a usable connection before installation; do not assume rollback or install from an unconfirmed in-memory intent.

For an identical existing preparation, reuse its frozen timestamps/records; do not create fresh publication IDs. A conflicting request fails. An already committed exact request returns the historical receipt after durable validation, without a new clock, grant or authority transition. Its receipt explicitly means `committed`, not `currently_active`.

### C. Install/verify bytes without SQLite ownership

Add an internal store operation conceptually named `stage_candidate_blob(prepared_record, content)`. It is available only to trusted composition and requires an exact replay-validated candidate preparation/intent; arbitrary caller records or constructed objects cannot authorize it. It accepts no Worker path. It must reject entry when the event connection already owns a transaction.

Use existing private root, bounded temporary file, 0600 permissions, file fsync, SHA-256 and atomic create-if-absent installation safeguards. For each member in ascending digest order, acquire only that digest's filesystem lock, then the existing process-wide mutex; read/revalidate its durable intent and set identity, verify/reuse or atomically install the immutable object, and fsync the directory. Reuse of an existing valid object also performs the directory durability barrier before reporting installation complete. Release the lock before moving to the next digest. Do not retain multiple digest locks and do not call `publish_bytes` recursively.

Stage returns only a private, ephemeral installation result. It appends no `ArtifactPublished`, grants no read, and does not cache candidate authorization. Every installed object is retained after any subsequent failure; stage does not unlink a final digest path. Its own unlinked, unshared temporary files may be cleaned during normal unwinding; crash leftovers and final/uncertain/existing objects are inventory only and never automatically deleted.

Installation is idempotent. Two publishers of the same prepared set may both inspect/install the same immutable digest and converge. Concurrent ordinary publication can reuse the same digest; neither path deletes the other's inode. The durable candidate intent exists before candidate installation, so an exception after link/fsync must not be described as no effect. Trusted immutability and the absence of automatic final-object deletion are required to carry installation evidence to the final transaction without holding digest locks. Later disk corruption fails at re-hash/read/recovery; no guarantee against hostile host replacement is claimed.

### D. Atomically commit all metadata and the set

After every member was verified and durably installed, collect a fresh outside-transaction recovery inventory, then open one short `append_checked` transaction. Validate the inventory version witness, re-read the complete preparation, corresponding intents and any prior commit, and compare private installation results with all frozen members. No path/file read, digest lock, grant issuance or child process is allowed inside this transaction.

Resolve current durable authority again, using a clock sampled after SQLite acquisition. Recheck full context, graph, policy, reservation/route, cancellation, active Attempt/Agent, fence and exact lease. All must still match preparation. Append all `ArtifactPublished` records using nested metadata-only appends on the same connection; they remain uncommitted. Complete the bounded metadata work and capture `authority_heads`, then take the final trusted clock sample. Require it to be nondecreasing from preparation and the earlier after-lock sample and strictly within the exact accepted lease. This final guarded sample is `committed_at`. Only after that check construct and return the single `CandidatePublicationCommitted` draft carrying that exact sample; `append_checked` appends the marker and commits the same outer transaction. Do not append a marker stamped with the earlier sample, rewrite a previously appended marker, or take another clock sample to choose its timestamp. No new authority-dependent work or filesystem operation follows this guard; the bounded marker append and outer commit complete the already decided operation. Any guard, marker-append or commit exception rolls back all final metadata and the marker; it cannot roll back installed files or the earlier preparation.

The **authority linearization point** is this final in-transaction guarded decision, conditional on the outer transaction committing. Cancellation/replacement writers are serialized by SQLite: one wins before this decision or follows the committed publication. Lease validity is measured at this point, after lock waiting and bounded metadata work, not at request arrival. Disk commit/return can occur after the wall-clock lease deadline; that does not renew the lease or authorize any later action. If the transaction fails there is no publication linearization, even if it had passed the check.

The **visibility point** is the SQLite commit of all publications and the set marker. Other connections see all or none when the complete cross-stream decision uses the single snapshot required below; separate autocommit reads may straddle this point and must not be joined. In-process candidate reads must use durable records only after successful outer commit; `_records` cache entries written during a nested append cannot authorize reads after rollback. The new finalization path must defer cache updates until outer commit or use no cache at all. This service requires the real readable SQLite store; no fallback-to-cache adapter is permitted.

If cancellation, expiry, graph change, replacement, release or reservation change wins, finalization rejects and leaves prepared/installed material pending. It never creates readable metadata as compensation. If finalization wins, later cancellation does not erase historical publications, but all future execution/acceptance still require fresh active authority. Publication returns no grant and cannot itself confer child access.

## Recovery separation and global lock order

Required global rule: **never acquire a digest lock or the publication mutex while owning a SQLite transaction**. Store filesystem sections may acquire one digest lock, then `_PUBLICATION_LOCK`, then perform bounded database reads/writes. Metadata-only control-plane transactions never request either store lock. No operation may hold the process mutex while waiting for a second digest lock. Sorting members is deterministic processing order, not permission to nest the existing `_digest_lock` contexts.

To preserve existing recovery checks without their current inversion, separate `RunRecoveryCoordinator` into two internal responsibilities, with names finalized in the later plan:

1. Outside SQLite ownership, capture complete artifact-stream membership, validated event versions/payload hashes and candidate-stream versions in a short database snapshot; end it, then verify published bytes and inspect pending content under existing per-digest locks. The private result records exact metadata plus observations and the captured stream witness. Capture includes all artifact stream IDs, not only known Run digests, so a newly introduced stream cannot escape comparison.
2. Under the caller's SQLite transaction, compare complete stream membership/versions/hashes with that witness, then perform lifecycle/Agent/budget/effect/provenance checks using only durable database state and the already verified inventory. A changed witness requires rollback and fresh collection outside SQLite. No stale cache or automatic fallback to filesystem work is allowed. Retry collection at most three times; continuous concurrent changes return a stable unavailable error, with no skipped checks.

The witness is trusted process-local evidence produced by the store, bound to that store/connection and operation; it is not a public model/capability accepted from callers. No public `skip_artifacts` option is introduced. New/replayed model data is still validated. Pending byte-presence observations may become stale when another process installs a previously missing object without changing metadata. They are labeled observations, never authority; this cannot authorize a read, success, deletion or automatic resume. Published bytes verified outside the transaction rely on the same immutable-store assumption as staging; every eventual consumer still re-hashes them.

Adapt every current outer transaction path that can reach full recovery: Scheduler active/verification resolution, routing acceptance, recovery planning, nested WorkerInputService operations and application startup. Public recovery still returns full verified artifacts; the database-only internal operation must not silently substitute empty inventories. Nested operations receive the outer operation's validated witness; they must not collect it while inside SQLite. Normal public operations called without an outer transaction collect their own witness first. Retrying after witness invalidation must not repeat already committed mutations.

Startup collects the required artifact inventories before its existing atomic recovery/Provider-settlement transaction, validates witnesses inside it, and reuses the same validated view for its before/after projections. It additionally audits all candidate streams and cross-links, including Runs with only preparation events. Capture and compare complete Run/config/lifecycle stream membership too: a newly introduced Run requires a new inventory, never an empty substitute. A concurrent artifact metadata write rolls back/retries that startup transaction; readiness is set only after a successful commit. This preserves atomic startup settlement and corruption rejection without doing filesystem I/O under its write lock. It does not replay publication or Worker execution.

This separation is required narrowly for lock safety. It does not change Provider reconciliation policy, lease decisions, budget accounting or legacy artifact integrity requirements. Cross-process tests must exercise the real indirect path, not only assert that the new service omits a direct `publish_bytes` call.

## Whole-set admission, reads and compatibility

New candidate publication records are detectable by their reserved protocol/source keys and publication-ID namespace. Conflicting/malformed combinations fail closed; they do not fall back to legacy behavior. Generic `publish_bytes` cannot create records in that namespace. A candidate preparation is also indexed by exact Attempt identity, so removing a source marker from an artifact or selecting an older legacy publication cannot bypass a preparation already known for that Attempt.

Add a shared, database-only set lookup/validation operation to the candidate journal. Given exact full context plus the complete normalized ArtifactRef list, it requires the unique committed set and its exact original preparation/intents/publications. It does not accept a caller-supplied receipt as proof. When an Attempt has a preparation, only that entire committed set is eligible; subsets, supersets, same-digest changed metadata and mixing legacy/publications from other sets reject. The absence of a commit is rejection even if all blobs exist or some digest has an independent legacy publication.

Every multi-stream candidate read must use one database-only snapshot spanning the first journal/member discovery read, preparation/commit replay, every member intent/publication, and relevant preparation-index/namespace checks. This applies to all consumers below, initial request lookup, historical retry, status, uncertainty resolution and startup/recovery audit. Begin a short read transaction before any discovery if none exists; dynamically discovered streams must be read before that same transaction ends. Reading the journal first and then calling a snapshot helper for its discovered members is insufficient. Reuse an existing outer transaction on the same connection when present; nested reads must not end the caller's transaction or establish a later view. The current `read_streams_consistent` facility may be reused or factored to support discovery within its transaction; its current fixed-key signature is not an existing dynamic-discovery API. No new global event-order mechanism is needed.

Finish the database-only validation and materialize its bounded immutable metadata result before closing an owned read snapshot. Close it on every success/error path before filesystem work, grant issuance or digest-lock acquisition. When reusing an outer transaction, return only database data to that owner; downstream filesystem/grant work must wait until the owner ends the transaction. A full store read or verifier path invoked under an outer transaction must fail closed before such work rather than close a caller-owned transaction. Staging may already hold its single digest lock before entering a short database-only lookup, consistent with digest -> mutex -> database order; the lookup must end before subsequent filesystem work, and never acquire another filesystem lock while SQLite is owned. Snapshot helpers never collect filesystem inventory themselves.

ArtifactStore read/metadata methods must load and validate their actual publication records, parent journal and all required member links inside this coherent view. They must not authorize using a publication list loaded before the snapshot joined to a later journal result; discard/reload any such list. After snapshot closure they may apply the normal grant and byte-integrity checks to that exact validated view. Candidate admission and verifier paths likewise use the metadata/set result from one view, rather than joining independent inventory and journal reads. A coherent earlier pending state is an ordinary ineligible/prepared result; a coherent later committed state is eligible subject to the remaining checks. Only a malformed linkage within a single coherent view is partial-publication corruption. A valid concurrent commit must never be classified as corruption merely because a reader previously observed another state.

Required consumers and their behavior:

| Consumer | Required candidate behavior |
| --- | --- |
| `admit_candidate_artifacts` | For a candidate-protocol Attempt/record, require exact committed-set lookup in addition to fresh model validation and existing byte/provenance verification. An inventory-only adapter unable to provide journal lookup cannot admit such records. |
| `IsolatedVerifierProcess.verify` | Perform the same whole-set gate before obtaining any digest grant or staging a byte. Preserve byte caps, re-hashing and exact provenance checks. Direct trusted verifier use cannot verify a pending or partial new set. |
| `AttemptExecutionCoordinator.accept_proposal` | After fresh authority/proposal resolution, require the proposal's complete candidate references to equal the committed set; then use the existing independent verifier and usage path. |
| `Scheduler.finish_verified_attempt` | Inside its terminal transaction re-read the set binding for candidate-protocol Attempts in addition to existing proof checks. No filesystem I/O is added here. |
| Scheduler historical success audit and application proposal/candidate startup audit | Validate historical set/context/publication linkage at the recorded publication/acceptance points. Do not require an old lease to remain active today. Never promote a preparation/proposal to success. |
| ArtifactStore grant reads/metadata APIs and verified Run inventory | Candidate `ArtifactPublished` metadata must resolve to the exact complete committed journal record. Missing/partial/malformed linkage fails closed before authorizing a read; this is defense against corruption, not a provisional-record visibility scheme. Existing grant scope and byte verification remain required. |
| Pending/orphan inventory | Report retained state with exact provenance, never candidate eligibility or reading authority. A shared digest with another publication remains pending for this candidate identity. |

Marker validation at the store uses a database-only journal helper to avoid recursive ArtifactStore reads. The journal validates metadata linkage but does not call grant reads or filesystem inventory. Whole-set validation is meaningful only with the requested full set; a per-digest read validates the parent set's complete metadata links, then applies that digest's normal grant.

Existing noncandidate-protocol publications and preexisting verifier proofs retain their current trusted-host semantics when no preparation exists for their Attempt. There is no grandfathering for a malformed candidate record or missing candidate marker, and no migration that invents a candidate set for old artifacts. This compatibility does not provide an alternate route for the new publisher: it always uses the reserved protocol and the preparation index. Existing low-level host publication remains a trusted host capability, never a Worker capability.

A valid publication makes bytes eligible for existing host-controlled Run-scoped grant policy; it does not issue tokens, widen another Run's scope, or attest redaction. Cancellation after a valid commit does not retroactively revoke separately issued host grants; current grants expire/consume according to existing rules. No child receives such grants here. The acceptance coordinator must resolve live authority before issuing verifier grants and recheck it on terminal completion, as today. This design adds no cancellation-time grant revocation guarantee and does not claim that publication is successful execution.

## Retry, restart and failure outcomes

The service returns an immutable, content-free receipt with `request_id`, `set_id` and durable state `committed` after exact replay. It is informational, never a capability or accepted Worker result. Propose `ControlPlaneApplication.candidate_publication_status(*, run_id, node_id, attempt_id, fencing_generation)`, a read-only ready-gated lookup returning `absent`, `prepared`, or `committed`, with the deterministic IDs when present. This distinguishes pending versus committed after response loss without resupplying bytes. Lookup must discover, replay and cross-check all records in the single database snapshot specified above, not trust an in-memory flag or join separate autocommit reads; corrupt/unreadable state raises the sanitized error and is never returned as absent. A concurrent valid commit may leave this lookup reporting the coherent earlier prepared state. It returns no candidate bytes, grant, active-authority claim or metadata from another identity.

Explicit whole-request retry is allowed; startup never initiates it. An exact already committed retry may return the historical receipt even after cancellation/expiry. To compare such a retry, reconstruct the validation task from the preparation's historically validated full context and durable original role/input commitment, check exact re-supplied text and decode the raw frame, then compare set identity. It must not call active task preparation first and thereby mistake committed-but-now-stale for a never-published request. No new write or read grant occurs on this path. New/prepared-but-uncommitted requests always require fresh current authority before more staging and at finalization.

| Interruption/failure boundary | Durable meaning and allowed recovery |
| --- | --- |
| Invalid request, failed early authority, or preparation transaction definitely rolled back before any prior intent | No candidate effect for this request. No candidate bytes installed. Do not generalize this to Worker/Provider execution being no-effect. |
| Preparation commit response lost or database unreadable | Outcome uncertain. Reopen/replay exact request and all intended records; no installation until complete durable preparation is established. Never delete or create a replacement identity. |
| Preparation committed; no blob installed | Pending known preparation. No new readable metadata. Explicit exact retry can revalidate authority and stage; startup reports only. |
| Crash during private temporary staging | Prepared/pending; temporary file may remain. No assumed installed object, no automatic cleanup or replay. Retry may create a new private temp after validation. |
| Crash/error during or after any individual link/directory fsync | Retain object if present; durability may be uncertain. Inspect under digest lock and re-hash/size/fsync on explicit retry. Never infer absence from missing metadata or delete a shared digest. |
| Some/all blobs installed, before final transaction | Pending; entire set ineligible. Retain all objects, even if Attempt is cancelled, expired or replaced. Explicit retry must revalidate current authority. |
| Authority invalid at final guard | No new candidate metadata/commit. Prepared state and blobs remain held as pending/observed stale. No success, settlement, release or automatic resubmission. |
| Failure after any individual metadata append but before outer commit | SQLite rolls back every final publication and marker. Earlier intents/files remain. No partial set is visible to other connections; in-memory caches must not leak rolled-back records. |
| Final commit outcome unreadable/response lost | Uncertain until replay in one database snapshot from discovery through all cross-links. Exact full metadata plus marker means known committed; preparation without marker means pending. Marker without all metadata or metadata without marker within that coherent view is corruption, not partial success to repair. A concurrent valid commit cannot create such corruption; never join observations from different snapshots. |
| Known committed, later cancellation/expiry/replacement | Historical committed publication remains, but current-authority operations fail independently. Never republish, issue a grant or mark success merely to answer a retry. |
| Restart with valid pending state | Report pending and content observations; preserve reservations/leases according to existing lifecycle recovery. No automatic publish, verifier run, Worker/Provider reexecution, metadata adoption, settlement or deletion. |
| Restart/replay with altered context/hash/header/record/stream order, missing committed bytes, invalid scope or duplicate/conflicting events | Fail startup/readiness or the affected operation closed. Retain evidence; no repair by guessing or deleting blobs. |

Recovery validates every candidate stream before readiness, not just entries referenced by a successful Node. Preparation must bind a real historical accepted Attempt, original full verification admission/role/planning/config/route/reservation and its recorded lease. Commit time must be nondecreasing from preparation and strictly within that lease. Historical audit reconstructs lifecycle/graph/cancellation/fencing and resource state through the recorded `authority_heads` prefixes for both phases; it must not compare against today's graph and falsely invalidate a formerly valid publication. The implementation must reuse/factor the existing projection reducers for prefix replay, not use a temporary database, mutate live projections or invent a global event-order interface. A prepared but uncommitted stale Attempt is valid retained history, not startup corruption. An orphan candidate intent, a candidate publication without its matching set, or a committed set missing a member is corruption. Generic older artifact intents retain their existing inventory semantics.

## Bounds and safe errors

Preserve decoder frame/content/count bounds: 1 MiB raw frame, 1..128 unique members, aggregate decoded bytes at most 16,384, and existing per-field strict limits. Bound frame and text before parsing/canonicalization; check encoded lengths before decoding as today. No streaming, large-output variant or limit increase is included.

The new journal allows at most 1,024 prepared requests per Run and at most 16 MiB of canonical candidate journal payloads, with at most 1 MiB per event payload. Preparation reserves a conservative 16,384-byte allowance for its possible commit, including its five authority heads; that allowance counts toward the Run limit until replaced by the actual commit payload, which must fit it. Head event identifiers are bounded to 128 characters in this protocol; payload hashes are exactly the existing 64 lowercase hex digits, and stream names/IDs have the fixed names or existing Run identifier bound. Count validation, existing exact retry and cap enforcement occur under the same SQLite write lock. Replays enforce the same counts/reservations, complete-set counts and finite limits. Identical retries at the cap remain no-ops; failed/conflicting requests do not grow durable history. There are at most two candidate events and two artifact events per member for a request. Installed candidate content is at most 16 MiB per capped Run, excluding preexisting/shared bytes and private crash leftovers; no automatic deletion policy is introduced.

Per-Run limits do not claim a global disk/memory quota across unlimited Runs or concurrent host calls. Concurrent-call limits remain the trusted host's existing orchestration responsibility. Canonicalization and recovery must enforce caps incrementally and must not allocate based on untrusted declared sizes. Store waits/SQLite busy errors produce unavailable/uncertain outcomes as appropriate; no retry spins or unbounded internal resume loops.

Expose only fixed `CandidatePublicationError.code` literals: `candidate_publication_invalid`, `candidate_publication_too_large`, `candidate_publication_conflict`, `candidate_publication_inactive`, `candidate_publication_unavailable`, and `candidate_publication_uncertain`. Classification is host-owned: malformed input/policy is invalid, proven cap violation too-large, validated same-request changed identity conflict, proven stale authority inactive, unavailable prerequisites with known state unavailable, and ambiguous durable effects uncertain. A generic internal exception after preparation cannot be labeled definite no-effect. Durable lookup is the authority for committed/pending state, not an exception code alone.

No raw frame, task text, bytes, Base64, proposed metadata strings, arbitrary backend messages, paths or child failure codes are included in owned exception args/code/repr, structured logs or owned context/cause chains. Raise a fresh allowlisted error after leaving owned exception handlers; `from None` alone is insufficient. Receipts omit content and input text; durable records contain only fixed host metadata, bounded identity and commitments. Hashes are not confidentiality or origin proof. Explicit access by the trusted caller and traceback locals/host memory are outside this redaction guarantee.

## Required later verification

The later implementation plan must use real filesystem and separate SQLite connections/processes for publication/locking/recovery assertions. Pure mocks are useful for failpoints but cannot establish atomicity or lock safety.

- Pin full valid vectors including binary/zero bytes, policy labels, canonical set/member identities and complete context. Mutated/unsafe decoder results, nested models, unknown fields, subclass fields, bools, incomplete/extra/duplicate members, result ID changes, declared-size lies, graph/config/policy/route/input/planning mismatches and unsupported outcomes fail before effects where applicable.
- Exercise exact byte/count/journal boundaries and retries at caps; verify space reservation permits a prepared request's commit. Preserve the distinct encoded-frame budget and all decoder regression tests.
- Race identical requests, changed same-Attempt requests, shared digests across Attempts/Runs, generic publication and publication retries. Assert one complete set, stable IDs/timestamps, no duplicated intent/metadata and no cross-Run read. Verify subset/superset/mixed-set paths against every consumer, including direct verifier and low-level Scheduler finish.
- Add deterministic real separate-connection/process reader tests with barriers after the first journal/member discovery read and before subsequent cross-link reads while another process commits the complete set. Cover journal-first and artifact-first orders, dynamically discovered members, shared digests, status, direct set gates and ArtifactStore read/metadata methods. Status may return the coherent earlier `prepared` or later `committed` state; gates may coherently reject pending or admit committed, but no path may report partial-publication corruption from this valid race. Assert store authorization uses the records loaded in that snapshot, not a preloaded list. Repeat inside an already-open outer read transaction and an outer write transaction: preserve the original view and transaction ownership; for the write case the writer barrier must show the competing commit waits until release rather than deadlock the test. Assert snapshot closure on success/error before filesystem locks/work or grants; nested database-only helpers leave the outer transaction open, and full read/verifier entry under it rejects before filesystem/grant work.
- Serialize cancellation, lease expiry, graph change, fence replacement and reservation release on both sides of prepare/finalize. Force SQLite lock waiting across the exact lease deadline and time advancing during metadata work. Assert all-or-none visibility and no success/resource/usage events.
- Pin `committed_at` with a deterministic advancing clock: the after-lock sample is lease-valid, metadata work advances time, and the exact final guarded sample is persisted in the marker. Final sample at/after expiry or earlier than either prior sample must roll back every metadata append without a marker; inject failure immediately after the valid guard, during marker append and at outer commit. Permit commit/response after expiry only when the persisted final sample was valid; no later authority or replacement timestamp may be inferred.
- A cross-process inversion detector must pause ordinary/staged publication after digest acquisition before SQLite, concurrently invoke active resolution/routing/WorkerInputService/startup/recovery, and assert bounded completion without SQLite-then-digest acquisition. Instrument the process mutex too; cover two threads and crossed digest order. Verify witness invalidation/new streams retry outside transactions and fail closed after the bounded retry count.
- Kill/fault before/after preparation, each intent, temporary fsync, every individual install/link/directory fsync, each metadata append, final guard, commit and response. - Keep production `IsolatedWorkerProcess` blocked-only and output transport untouched. Run the full existing suite with total coverage at least 90%, focused relevant tests, compile/dependency/wheel/source-equivalence/whitespace checks and independent task/whole-slice review before controller push. Required existing real systemd isolation tests must run without skips when making that isolation acceptance claim; new database/filesystem tests do not themselves prove isolation or functional Worker execution.

## Explicit handoff exclusions

This slice does not generate Worker output, connect decoder/publication to stdin/stdout, launch a functional Worker, expose child file paths/capabilities, grant a Tool/Provider request, perform semantic/project-test/Final Review, implement production usage or settlement, wire Gateway/Approval/Secret Broker, deploy, use real credentials or incur paid Provider activity. Verifier proposals and trusted usage remain separate prerequisites; publication alone never settles a reservation or finishes a Node.

The existing production stdout budget is 16,384 encoded bytes. A 16,384-byte binary artifact requires 21,848 Base64 characters before JSON and metadata. Decoder acceptance cannot prove that frame can traverse the current transport. Future transport integration must separately review its encoded-frame budget, process origin, termination and limits; this design changes none of them. Larger/streaming output is excluded.

The controller's next action is independent architectural review of this spec, including the recovery separation and historical ordering audit. Only after findings are resolved does a separate implementation plan become appropriate. There is no pending product implementation, source-test execution or plan writing within this design task.
