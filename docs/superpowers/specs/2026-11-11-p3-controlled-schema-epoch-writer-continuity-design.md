# P3 controlled schema epoch and writer continuity — design for review

Status: proposed, not implemented and not evidence of deployment readiness. This addendum refines the “Bounded shared artifact evidence” section of `2026-11-07-p3-worker-host-mediation-stop-proof-design.md`. It preserves that section's conditional status and its complete bounded fallback. The existing experimental DIRTY/checkpoint/rebuild implementation is diagnostic only. A clean marker, this document, or a successful test is not a permit, read grant, stop proof, cancellation proof, or reservation.

## Objective and trust boundary

Define what a deployment must establish before it can even consider a bounded incremental artifact checkpoint as evidence. The user has chosen to trust other host processes under the same UID for this design: they do not intentionally forge authority, alter the broker, schema, database or evidence, or bypass the agreed protocol. Constrained Workers, tools and all external inputs remain untrusted, even if a Worker has that UID. Accidental races, a stale executable or connection, crashes, queued operations, lost replies and storage errors remain in scope. Trust in a host peer is not proof that it is correctly configured, that every writer is known, or that a filesystem is reliable.

The trusted computing base must include the controlled store service, its configured executable and libraries, host administrator, boot/OS isolation, SQLite and its approved VFS, the external epoch guard described below, and storage/durability semantics. Administrative access, privileged processes and same-UID trusted host peers must respect the protocol. This design does not defend against a malicious administrator, a compromised trusted host peer, or arbitrary physical disk modification. Worker-controlled paths, SQLite files, SQL text, extensions, TEMP objects, database handles and FDs must never reach the trusted store capability. A Worker must not acquire a broker filesystem namespace, inherited descriptor, service credential, writable database mapping or arbitrary SQLite access; prove these properties for each actual sandbox profile, not merely one fixture.

## Concrete current gaps

* `SQLiteEventStore` opens a pathname, initializes schema, and allows separate thread-affine instances. `open_read_only` opens another pathname connection. `Application`, standalone `ArtifactStore` and the secrets server each create or can create stores; caller-supplied event-store capabilities and generic SQLite connections/snapshot APIs need explicit review. `_OwnedConnection` and the trace observer track one connection's transaction, not all processes, raw Python base-class access, native SQLite connections or filesystem writes.
* `transactional_dirty` audits current persisted DDL, indexes and the current connection's TEMP triggers; another connection's TEMP trigger is invisible. A trusted but stale writer can use old code or a connection created before installation. DROP/mutate/restore can return the same fingerprint. `register_digest` starts DIRTY and a complete bounded rebuild makes only a diagnostic clean marker. The incremental append and rebuild paths can update that marker, but their present caller and database identity are not authenticated.
* `SQLiteEventStore` currently enables WAL through a pathname connection; a held pathname, a DB-only inode check, a fingerprint or an advisory lock does not prove that SQLite's actual file handles, WAL and shared-memory file refer to the expected database or that another process cannot open an alias. An earlier `/mnt/c` process-lock fixture is not proof of production filesystem semantics. No suitable storage-identity or complete writer-inventory implementation is established today.

### Entry-point coverage and compatibility requirements

The current inventory below is a starting map, not proof that no other process, package, native binding, admin script, test harness or deployed binary can access the DB. Each deployment must produce and validate its complete inventory.

| Existing entry | Controlled-epoch treatment | Legacy/non-opt-in treatment |
| --- | --- | --- |
| `SQLiteEventStore.__init__` → `_open_connection` → `initialize_schema` | Replace or gate the entire open and initialization path before the first connection or migration statement, including WAL selection and `CREATE TRIGGER IF NOT EXISTS`. Only the steward's factory may migrate under a non-ACTIVE epoch. A post-constructor capability check is too late. | Preserve existing constructor/migration behavior; it supplies no epoch evidence. |
| `SQLiteEventStore.open_read_only` → independent `sqlite3.connect` | Admit through a steward-owned read capability bound to the same DB, VFS and sidecar namespace, with no SQL/TEMP/extension escape; otherwise do not use for incremental proof. Treat its open lifetime and SQLite read-side WAL/SHM behavior as part of fencing. | Keep ordinary read-only use, without claiming a controlled snapshot or writer inventory. |
| `SnapshotStore` from a path | Route through the controlled factory before its `_open_connection` and unconditional `initialize_schema`; validate its snapshot reads/writes and migrations in the same policy, including interactions through triggers. | Preserve existing path-based behavior; no epoch status follows. |
| `SnapshotStore` from a raw `sqlite3.Connection` or an object exposing `_connection` | A foreign connection, even if it currently points at the right pathname, is not admissible. For controlled mode, replace raw sharing with a steward-owned typed snapshot capability or an explicitly validated internal handle whose lifetime and all SQL remain under the steward. Do not take ownership of or silently mutate a caller's connection. | Preserve the existing accepted raw/shared connection contract outside controlled mode. |
| `OrchestratorApplication`, standalone `ArtifactStore` and its separate `.metadata.db`, custom injected event stores, secrets-server per-request stores | Route each actual database and connection independently through the relevant approved steward; verify service/thread lifetime and caller capability before any open. A custom event-store implementation is ineligible unless explicitly inventoried and independently proven equivalent. Separate metadata DBs require separate instance/epoch identities. | Preserve current injectable and standalone modes, without automatically promoting their diagnostics. |
| `append`, `append_checked`, artifact publication intent and publication | Admit every public and internal call, including `append_checked` delegation and both intent and publication appends, under the same policy and correct transaction binding. Two appends are distinct transitions unless an explicit enclosing owned transaction proves atomicity. Raw SQL, direct `_connection` use and unknown ambient transactions never inherit the controlled capability. | Keep existing semantics; an ambient transaction may use a savepoint but that does not make it owned or permit diagnostic clean. |
| Direct SQLite, administrative migrations, backup/restore, foreign runtimes or old binaries | Fence/drain or route through a reviewed compatibility capability before epoch establishment; enumerate read/write access, callbacks, TEMP triggers and prepared statements for every permitted connection. Existing pre-opened handles and unknown scripts are not retroactively admitted. `BEGIN IMMEDIATE` serializes a transaction but does not establish this inventory or prevent later access. | A deployment that must retain uncontrolled access stays legacy/non-authoritative; no shared artifact digest is frozen. |

`CREATE TRIGGER IF NOT EXISTS` can restore a missing trigger during startup and make a prior DROP/mutation/restore invisible. Startup must therefore consult and transition the independent epoch guard **before** running any such migration; seeing the expected trigger afterward cannot repair the trust gap. For any per-connection authorizer, prevent statement-cache and prepared-statement bypass: install it before preparing statements, invalidate/finalize statements on policy transitions, include trigger-origin authorization, and test actual SQLite prepare/reprepare behavior. Even perfectly enforced on that handle, it cannot inspect another connection's TEMP schema or stop direct file writes.

## Proposed control model

### Enforced store boundary and writer inventory

Introduce an opt-in **store steward** as the sole authority over a specific database instance and every SQLite connection which can access it. This is a proposed host component, not an existing class or claim. Its deployment manifest names the DB instance, supported SQLite/VFS and journal/durability settings, exact binary/migration/schema versions, root paths and every authorized entry point, including recovery, backup, restore, admin tools, read-only/watch connections, standalone artifact metadata stores, secret-broker threads, snapshots, tests and upgrade/downgrade paths. The inventory is an audited deployment artifact, with owner and version, not a scan of process names or a list inferred from source grep. A connection is eligible only when it is created under the steward's controlled factory, its configuration and provenance are verified before its first statement, and its lifetime remains inside that boundary.

Preferred first implementation is a single steward process exposing narrow typed operations and owning all database handles; callers and Workers never receive raw SQL, database paths as authority, connections, attached databases or file handles. If multiple steward processes or factories are later supported, each must meet the same admission, per-connection hardening, coordination and fencing requirements; a local lock without enforced participation is insufficient. A dedicated OS principal or comparable enforced isolation should restrict DB directory, DB, WAL, shared-memory and control-plane access to the steward and specifically trusted operations. If same-UID separation cannot be enforced, eligibility requires an explicit deployment assumption that all trusted same-UID peers are inventoried and do not open or manipulate these files, plus an independently checked operational mechanism that rules out stale/uncontrolled connections before opt-in. This is an assumption, not a consequence of `flock` or this user's trust choice. If the deployment cannot establish that assumption, leave incremental evidence disabled.

The isolation requirement is continuous, not a one-time inventory or drain: from before `ACTIVE` is published until after the last transaction/result has completed and the epoch is retired, an independently enforceable OS/VFS/supervisor boundary must prevent **every** unadmitted process or connection, including processes started later by mistake, from reading or mutating the protected SQLite DB/WAL/SHM namespace in ways outside the approved protocol. This includes an old binary launched after activation and any connection that could create a TEMP trigger or use raw file I/O. Enumerating processes once, checking a deployment manifest, a cooperative lock, same-UID trust and promises to follow the protocol cannot exclude a future misconfigured trusted peer and do not establish continuity. Identify the concrete isolation primitive and principal, protected mounts/paths/handles, admission and revocation rules, supervisor start policy and operations for the actual deployment, and demonstrate they remain enforced during ACTIVE, failure and handoff. If the platform cannot enforce or independently verify that boundary for its actual runtime, keep incremental state non-authoritative for the entire deployment and use the complete bounded fallback or hold. Detecting an attempted access is not a substitute for excluding a successful unobserved access.

An unmodified legacy writer that can open the database is outside the controlled epoch, including a connection that installs a TEMP trigger after another connection inspected its own TEMP schema. Do not label it controlled just because the persisted triggers normally dirty its writes. To preserve v1, either route its operation through a compatibility adapter that uses the steward's authorized typed writes and maintains its externally visible contract, or keep that database in legacy/non-authoritative mode and use the existing complete bounded validator or hold. Do not freeze a digest or silently block an otherwise valid legacy write simply to obtain proof. Enabling the controlled epoch may change availability for an opted-in deployment; DDL/trigger and diagnostic write failures can roll back a legitimate write, including SQLITE_FULL, IOERR and unclassifiable permission failures. The non-opt-in behavior is unchanged. An already-open legacy handle must be closed or externally fenced before establishment, not merely discovered after the fact.

Capability admission is a host-side contract, not a bearer token supplied by a Worker. A new connection must not inherit unreviewed TEMP state, custom collations, functions, extensions, attached databases or replacement authorizers; verify `recursive_triggers` semantics for each connection and enforce the approved setting(s). Verify every actual operation, including writer startup/migrations, connection pooling, hooks and failure paths, against the closed writer inventory. No arbitrary `ATTACH`, `DETACH`, TEMP DDL, `writable_schema`, `load_extension`, schema mutation, raw transaction-control, unsafe pragma or ad hoc SQL through the capability. Account for indirect effects from triggers and callbacks, and prevent post-finalize SQL from bypassing the same restrictions. Connection-local `sqlite3_set_authorizer` can be a defense in depth on a handle owned for its entire lifetime; it cannot police another connection, an escaped base-class handle, external file edits or a restored schema. Do not overwrite a caller's authorizer to infer a denial's source.

### DB, WAL and lock-domain identity

Before accepting requests, use a capability-proven, filesystem-specific anchoring scheme that binds **the actual handles used by SQLite**, not just a checked pathname, to an approved directory and database identity. The scheme must handle no-follow traversal, path aliases/hard links, parent and mount replacement, file type, owner/mode/ACL, stable lock identity and descriptor inheritance, and retain the identity anchor for the entire epoch. It must show that the SQLite VFS and connection use the approved DB and sidecar namespace without a check/open race. If the standard Python SQLite API cannot establish this binding, provide a vetted VFS or an equivalent OS-supported mechanism; otherwise hold, rather than claim `stat` before/after or `/proc` observations suffice. Network filesystems, drvfs, different mount namespaces, custom VFSes and Windows-native access are unsupported until their locking, identity, atomicity and durability properties have been separately demonstrated and accepted for the deployment.

Bind the epoch to an externally authenticated DB-instance identity plus current boot/host and directory/mount/DB-file identity as appropriate; the DB's own UUID is useful for mismatch detection but cannot detect cloning or rollback of itself. Guard the SQLite `-wal` and `-shm` names and all other journal, checkpoint and temporary files in the same protected namespace. WAL creation, deletion, reset and checkpoint are legitimate SQLite lifecycle events: a fixed WAL inode is **not** an epoch invariant. Instead, require the approved VFS/namespace to account for each opened sidecar and prove it belongs to the same DB/locking domain; validate allowed transitions and hold on unexplained replacement, alias, loss or I/O failure. Establish compatibility with SQLite's actual VFS behavior under concurrent readers, checkpoint and restart, including open handles. Neither an inode nor a generation token proves durable contents or prevents ABA by itself.

Acquire an installation-controlled, non-replaceable ownership/fencing guard before DB open and keep it through the last possible writer/reader operation and any transition out of the epoch. Guard identity must be checked against an anchored object, not recreated by pathname; a second live holder or lock-file replacement is a hold. It must cover all participating processes; failure or uncertainty means no incremental eligibility. A lock released by process death proves neither durable commit, SQLite storage integrity, nor that an external SQLite client has stopped. A mere advisory lock plus an uncooperative old writer is not an implementation of this boundary.

### Epoch establishment and durable continuity

Epoch states are `ABSENT`, `ESTABLISHING`, `ACTIVE`, `UNCERTAIN`, and `RETIRED`; per-digest marker states remain diagnostic `DIRTY`/clean with version and checkpoint. An external, host-controlled guard outside the mutable DB must identify the installation/DB instance and durably record transitions in a storage domain with specified ordering, monotonicity and crash behavior. It is not enough to write a UUID or generation row inside the same database: copying/restoring the database also restores that row. This external guard is a deployment dependency, not yet established or claimed available. It may be a protected durable journal with an independently reliable monotonic generation, or a stronger equivalent; a normal file on the same replaceable filesystem, a hash, or wall-clock timestamp alone is not sufficient. Specify and test its recovery protocol and authority separately.

1. Establish exclusive producer exclusion and prove that all older connections, actors with DB access and pending migrations have been drained or fenced. If this cannot be demonstrated, stay `UNCERTAIN`; do not mark existing data clean merely by installing triggers.
2. Durably record a new unique epoch as `ESTABLISHING` **before** permitting any covered write. Under the approved connection and an owned SQLite write transaction, validate schema, triggers, index definitions, unique constraints, current TEMP schema and SQLite/VFS settings, then install or migrate the known tracking protocol atomically. The durable DB record binds its instance ID, epoch and schema/writer policy versions; it is a consistency check, not its own root of trust. New markers start DIRTY. Previously diagnostic clean markers from an earlier/uncontrolled epoch cannot be promoted.
3. Under producer exclusion, establish the storage anchor and ensure the DB committed transition is durable under explicitly specified SQLite journal mode, `synchronous`, VFS and filesystem assumptions. Publish `ACTIVE` only through a reviewed crash-safe handshake with the external guard. There is no assumed atomic commit across SQLite and the external guard: enumerate and test every crash cut. Any ordering with an ambiguous/missing receipt, failed fsync, unknown commit or inconsistent generation returns `UNCERTAIN`, not ACTIVE. Do not infer commit durability solely from a successful `COMMIT` or from an external counter update.
4. A digest becomes a candidate for diagnostic clean only through a fresh, bounded physical scan from the first row, complete version/orphan/tail and envelope/hash/business validation, and exact index rebuild in one owned transaction under the same ACTIVE epoch. Reject an absent or malformed registration, unknown history and over-budget data. Store the epoch and validated boundary in the checkpoint, and atomically install index and clean state; a failed rebuild, crash or rollback restores the previous state or holds. A clean marker alone is never a credential. Rebuild is per digest and never a shared-digest freeze; old data too large to validate can remain held indefinitely.
5. Controlled writes and candidate incremental reads bind the same epoch, DB instance, connection capability, transaction token and rollback generation. In one SQLite write transaction validate the live epoch and schema policy before use, establish pre-write clean, validate all new events and index effects, then restore clean only after the last controlled side effect. Any subsequent covered SQL, including after a savepoint, marks DIRTY in that transaction. Recheck epoch, DB identity, schema coverage, marker, stream version and physical boundary in the same owned snapshot used for a future proof; do not consume cached state after rollback, external state change or connection replacement. Commit ambiguity holds. The current full-stream append cost and bounded maintenance limits remain as implemented until separately redesigned.

The steward must hold a verifiable exclusive epoch lease/fence continuously from the identity and policy checks through each transaction's final commit/rollback and any publication of its result. A guard health check at transaction start, a later check after commit, or an in-memory token is insufficient if authority can be revoked or another producer admitted between them. Define whether guard loss revokes authority synchronously; if this cannot be enforced, no transaction spanning that uncertainty may return eligible evidence. Any later consumer must hold the same proven continuity through its own atomic decision; a detached result or stale lease cannot authorize a later action. Cross-process guard admission and migrations require a barrier which prevents a new writer from joining between the drain and activation; guard changes themselves are covered by the crash-order matrix.

A clean shutdown requires a durable quiescence/fence protocol: stop admissions, drain or classify all outstanding handles and transactions, checkpoint/flush as required, and verify identities. While continuous exclusion and the guard are still held, durably transition the external epoch out of ACTIVE to `RETIRED` (or `UNCERTAIN` if any part is ambiguous), then record clean close and only afterward release the guard and storage access. If the retirement cannot be made durable, preserve exclusion or classify continuity as uncertain; never release and leave a durable ACTIVE record that a later process can reuse. No close marker may race a writer.

Every ordinary restart, including after a clean close, establishes a **new** epoch and requires a fresh complete bounded rebuild for each digest before diagnostic clean or candidate eligibility; otherwise use the independent safe full-validation fallback or hold. A later design could optimize this only after independently proving continuous writer exclusion and storage identity/integrity for the entire shutdown gap, including all guard handoffs and crash cuts; a clean-close record alone is not that proof. If an old binary writes, creates a TEMP trigger or resets a marker during the shutdown gap, the next startup must never reuse the old clean state: assume such changes possible, create a new epoch, and rebuild from current physical history or hold. If the steward, host or guard crashes, is killed, loses its guard, or cannot prove the sequence, restart starts `UNCERTAIN` with the same new-epoch and rebuild requirement. An old session, PID reuse, reopened fd, old WAL or matching schema hash cannot resume it. If independently protected durable transaction journaling is proposed later to preserve continuity across crashes, its ordering, reconciliation and anti-rollback semantics require a separate proof and review; this design does not assume it.

### Schema/trigger policy and migration

For an ACTIVE epoch, keep an immutable, versioned **policy** for table DDL, every relevant unique/primary index (including origin, ordered fields, collations, expressions and partial predicates), foreign keys, all persistent triggers on every potentially interacting table, connection-local TEMP triggers and registered functions/collations. A strict allowlist can conservatively reject additional objects; a schema hash alone is only a mismatch check. Preflight SQLite metadata names, SQL types/lengths and row counts before Python materialization and reserve/charge every query, row and byte against the proof budget. Validate both recursion settings where supported, all `INSERT`/`UPDATE`/`DELETE`, REPLACE's implicit deletes with recursion off, UPSERT and old/new digest migrations. The explicit marker protocol must avoid recursion and cover updates to events, stream versions, checkpoints and publication index without affecting unrelated digests.

Checking only at proof time cannot detect DROP → mutate → restore or TEMP triggers on another handle. Prevent unauthorized DDL and TEMP creation for the **entire** epoch through the enforced connection boundary. Every schema migration, extension/collation or writer-policy change first stops admissions, fences all old handles, durably makes the external epoch non-ACTIVE, and completes or rolls back the change under exclusive ownership; then establish a new epoch and rebuild affected digests. Crash in any migration interval remains `UNCERTAIN`; restored identical SQL does not resurrect the old epoch. SQLite authorizers, `schema_version`, `data_version`, SQLite trace callbacks and file timestamps are corroborating observations, not a complete cross-process barrier. Operations changing the VFS, journal mode, databases, sidecars, backup/restore or storage mount are treated as epoch changes. Test both persistent and current-connection TEMP trigger cases; deliberately demonstrate that another connection's TEMP state is unobservable and hold unless the enforced writer inventory excludes that connection.

## Operational outcomes and evidence limits

A failure to establish writer coverage, handle binding, epoch continuity, exact policy, identity, an unambiguous commit, a budget or known storage behavior returns a redacted hold for incremental evidence. It must not convert `DIRTY`, missing state or an exception into clean, silently retry an unknown external Provider result, grant artifact access, release work or report stopped. Existing v1 complete bounded validation remains available where it independently proves its result; this architecture does not change v1 grants or digest association privacy. Record internal, bounded reason codes without exposing unrelated publications. Do not swallow or misclassify SQLite FULL/IOERR or trigger-write failure. A failed opted-in diagnostic maintenance operation can fail the whole SQLite write; disclose that availability cost.

Under the stated deployment assumptions, successful tests can establish that specified admitted connections follow the protocol, covered SQL mutations atomically dirty their affected digests, and tested crashes fail closed. They cannot establish absence of unobserved writers, privilege leaks, unknown filesystem behavior, stale database/WAL restore, silent page corruption, whole-machine rollback, malicious host administrators or a compromised trusted steward. An external root must itself have separately verified continuity and recovery; without it the result remains diagnostic even if every test passes. A full bounded validator also cannot establish provenance or physical integrity outside its read view. These limits are part of the acceptance decision, not outstanding warnings to wave away.

## Verification matrix and staged implementation

Use temporary isolated databases and self-created processes only; no real Provider, credentials, network calls or shared production storage. Every claimed invariant needs both a positive case and a failed/ambiguous case, and deployment-specific tests cannot be generalized to another filesystem or VFS.

1. **Inventory and capability foundation (non-authoritative):** catalog actual constructors and all public/internal write/read/migration/backup/recovery paths; test separately spawned app, standalone artifact store, secret server, raw SQLite and read-only connections. Establish supported capability/identity and deny leakage to Workers; characterize how old executable and pre-existing open connections are drained or excluded. Test forged capability, FD inheritance, alias/hard-link/symlink, replaced directory/lock/DB, mount change, mixed VFS and guard loss. No trusted epoch if an uncontrolled writer can still act.
   During ACTIVE, intentionally launch a real stale/old process after the initial inventory and attempt direct DB/WAL/SHM and raw SQLite access, including a TEMP marker-reset trigger; prove the actual enforcement denies it for the entire session, not merely that the process was absent at startup. Repeat with a future process admitted through each relevant service/supervisor entry. If any such access succeeds or exclusion cannot be demonstrated, the fixture must not report ACTIVE eligibility. For a clean shutdown, deliberately allow an isolated old process to mutate history or reset a marker via its own TEMP trigger in the period after guard release and before restart; verify the old epoch is RETIRED, restart creates a distinct epoch, and old clean state remains ineligible until a fresh full per-digest rebuild or hold. A test that only observes a marker or checks final schema is insufficient.
2. **Epoch state machine and crash ordering (non-authoritative):** implement a fake external durable guard first, then a concrete independently reviewed host implementation. Test failures and SIGKILL at every DB/guard prepare, commit, fsync, close and handoff boundary; restarts, same DB ID with replaced file, stale DB/WAL pair, old guard generation, clone/restore and concurrent startup/upgrade. No test double is deployment authority. Verify replay/ambiguity falls to UNCERTAIN. A clean shutdown must not race a writer; startup after unclean death forces fresh eligibility.
3. **SQL schema and writer coverage:** independent real processes exercise all four covered tables, all mutations, conflicts and REPLACE/UPSERT under both recursion settings, primary-key migrations and unrelated digests. Attempt bypass with direct old writers, already-open handles, TEMP triggers on another connection, raw SQL, custom collations, connection/base-class escapes, `ATTACH`, schema edits and unauthorized helper methods. A persistent trigger DROP/mutation/restore under an unauthorized connection must be excluded by the boundary or invalidate the epoch; merely detecting the final schema is insufficient. Migration/startup races, nested savepoint rollback, stale cached proof and finalization followed by untrusted SQL must hold.
4. **DB/WAL integrity and failure characterization:** real same-filesystem WAL checkpoint, truncate/recreate and concurrent readers; sidecar/DB replacements, stale copies and file aliasing; controlled `max_page_count` FULL in event write, marker trigger and checkpoint/index finalize, I/O failure injection only where faithful, rollback failure and uncertain commit. Close/reopen and independently compare event/version/index/marker. Process SIGKILL is not power-loss evidence. In-place older-page corruption and DB/WAL rollback fixtures must distinguish what is detected from what is impossible to detect without the external storage premise.
5. **Differential proof prerequisites, still disabled:** compare any later candidate bounded read with existing full validator for generated valid streams and all known corruptions; shared-digest old writer vs proof in both lock orders; exact publication/business fields, budget accounting, unrelated digest isolation and no association oracle. Verify complete late-run reservation and authorization/stop evidence separately before even proposing integration. No diagnostic result authorizes runtime behavior during these stages.

Implementation must be split into small reviewed, tested slices with unsupported environments fail-closed. Complete writer inventory, enforceable VFS/OS boundary and external durable guard are explicit go/no-go prerequisites, not implied by the task or user authorization to develop. If one cannot be implemented in the actual deployment, ship only non-authoritative observations and keep using the safe existing fallback. V2 launch, permit, ACK, stop, seal, Provider dispatch/retry, reconciliation of unknown outcomes, PR/production rollout and main-branch integration are outside this design; `outcome_unknown` is never resent on the strength of an epoch or lock.
